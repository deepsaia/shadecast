The surrogate model pipeline

How shadecast learns a fast stand-in for the physics, what the stand-in knows, how well it does, and where it stops.

Numbers from the model manifests and recorded runs of 2026-08-26, read on 2026-10-23. Model response-unet-ahmedabad-20260826T143800.

01What the surrogate is

The physics engine, SOLWEIG, computes mean radiant temperature for one square kilometer in 160 to 360 seconds. A plan search needs thousands of evaluations. The surrogate is a neural network that predicts the engine's answer in 0.58 seconds.

The network is a U-Net. It has 7,764,193 parameters. It reads seven input maps at 1 m and writes one output map at 1 m. Its receptive field is 152 m. Measured cooling from a tree falls below 0.1 C within 26 m in Ahmedabad and 71 m in Lagos, so the field is wide enough.

The surrogate is a forward model. It predicts the cooling a plan produces. It does not choose the plan. Planners choose plans. The surrogate tells them, quickly, what each plan does.

02Inputs

The model reads seven channels for every pixel. Each channel is divided by a fixed number, so every city uses the same scale. The numbers are not fitted. This is what lets a model trained in one city read another.

03Output

The output is one map. Each pixel holds the daylight-mean change in mean radiant temperature, in degrees Celsius. Daylight is 08:00 to 18:00 local time on the design day. A positive value is cooling.

The target comes from two engine runs: the untouched bundle and the bundle with the plan. The difference is the response the model learns.

04How the data is made

Physics time is the budget. One engine run yields one response field. The design set makes each run count. The Ahmedabad model used 17 runs.

FamilyRunsCoverage of plantable groundWhy
sparse probe4about 100 isolated trees on a jittered 100 m latticeeach tree is an independent response, so one run gives about 100
clustered61, 2, 5, 10, 20, 30 percent in 20 m blobshow planting happens; where responses overlap and stop adding up
random uniform41, 5, 10, 20 percentthe scattered extreme
corridor32, 5, 10 percent along the open-network skeletonthe street tree case

Each response field is cropped into 24 patches of 256 by 256 pixels. The sampler favors ground within 80 m of a tree and keeps a 5 percent floor elsewhere. Ahmedabad gave 416 training patches and 128 held-out patches. Ahmedabad and Lagos together gave 832 and 256.

The split

Patches from one design overlap and share context. A random split of patches would leak. The split is by design. A quarter of the designs are held out whole. The test asks whether the model predicts an intervention pattern it never saw.

A second split holds out a whole city. That asks whether the model transfers to geometry it never saw. The two questions are different. The pipeline reports both.

06How it is judged

Pixel error alone is the wrong measure. The response is near zero almost everywhere. A model that predicts zero everywhere has a small error and is useless. Four questions decide, in this order.

  1. Does it beat predicting nothing? Skill is 1 minus the model error over the error of predicting no change. Zero means no better than nothing. One means perfect.
  2. Does the tail survive? Error is reported by distance from a tree, from the tree itself out to 80 m. The far bands are the spillover.
  3. Is the plan score right? Plans are scored on population-weighted exposure, which integrates the whole field. That integral must be unbiased.
  4. Does it order plans correctly? A search only needs to know which of two plans is better.

07How it is used

Today the surrogate is used for one thing: assessment on designs it never trained on. No published number comes from it. Every number in the results comes from the engine.

The planners do not use it yet. Greedy and the orchard planner rank baseline harm and place trees. A surrogate-backed search is planned. The loop below is the plan, not the present.

08Where it falls short

These are the things that physics time did not allow. They are recorded so nobody mistakes an untested case for a tested one.

  • One design day per city. The model has seen one sun path and one season.
  • Trees only. Shade structures, de-paving and cool surfaces have no input channel.
  • 17 runs per city and 4 held-out designs. A ranking over 4 items proves little.
  • A transfer curve with two points, from one held-out city.
  • No search of settings: one learning rate, one width, one seed.
  • No uncertainty. One network cannot say where it is guessing.
  • No engine verification of a search, because no search uses the surrogate yet.
  • The sky openness channel is a proxy. The engine computes the real sky view factor for every baseline run and nobody reads it.
  • No augmentation. A flip or a rotation mirrors the sun path and puts shadows on the wrong side. Augmentation needs a sun-direction channel first.
  • Patches favor ground near trees. The far field is under-represented despite the floor.
  • Batch normalization with a batch of 8 on one device.
  • The checkpoint is a pickle with one metadata field. The manifest now fills that gap.

09How to train it better

In order of value per engine hour. Each item is a GitHub issue.

  1. Keep the best epoch and stop early. Done, issue 99.
  2. Write a manifest with every model. Done, issue 98.
  3. Read the sky view factor and the shadow fraction from the baseline run, and add a sun-path channel from the design day and latitude. Issue 100.
  4. Give each trusted intervention kind its own placement channel. Issue 47.
  5. Define the validation protocol: folds by design, a held-out-city curve over fifteen cities, engine verification of every chosen plan. Issue 101.
  6. Train five seeds and report where the spread is wide. Issue 102.
  7. Then regenerate the physics and retrain every selected tile with manifests. Issue 105.

10The manifest

Every trained model lives in its own directory with a file named manifest.json. The manifest says what the model is. A reader with the manifest and no code can decide whether to trust it.

SectionWhat it holds
model_id, createdresponse-unet, the cities, the time of training

11Where models live

Models, data and results are not in git. They live under data/, which git ignores. The layout puts each tile's models beside the physics that trained them.

data/tiles/<urban center id>/<tile id>/
  bundle/        the five layers, provenance.json
  surrogate/     baseline/ and one directory per design
  models/        one directory per trained model: model.pt, manifest.json, assessment.json
data/models/     models trained on several tiles

Storing models elsewhere is an option, never a requirement. A model store interface will have three backends: a local directory, which is the default, the Hugging Face Hub, and a git-lfs repository. Each holds the same files. Fetching from a public store needs no account. Publishing needs the credential that store asks for, at build time. This is issue 103.

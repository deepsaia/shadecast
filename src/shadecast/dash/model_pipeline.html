The surrogate model pipeline

How shadecast learns a fast stand-in for the physics, what the stand-in knows, how well it does, and where it stops.

Numbers from the model manifests and recorded runs of 2026-08-26, from the model definition, and from a receptive field measurement of 2026-10-23. Model response-unet-ahmedabad-20260826T143800.

01What the surrogate is

The physics engine, SOLWEIG, computes mean radiant temperature for one square kilometer in 160 to 360 seconds. A plan search needs thousands of evaluations. The surrogate is a neural network that predicts the engine's answer in 0.58 seconds.

The network is a U-Net with 7,764,193 parameters. It reads seven input maps at 1 m and writes one output map at 1 m. Section 03 opens it up stage by stage.

The surrogate is a forward model. It predicts the cooling a plan produces. It does not choose the plan. Planners choose plans. The surrogate tells them, quickly, what each plan does.

02Inputs and the grid

The grid

A tile is one square kilometer of city on a grid of cells 1 m by 1 m. One cell is one pixel. A tile has 1,000 by 1,000 pixels, which is 1,000,000 pixels.

A channel is one number for each pixel. The model reads seven channels, so it reads 7,000,000 numbers for one tile and writes 1,000,000.

Training does not use whole tiles. It uses patches of 256 by 256 pixels, which is 65,536 pixels, cut from the response fields. Section 05 says how.

Prediction uses whole tiles. The network applies the same small filters at every position, so it accepts a map of any size. One tile is predicted in one pass. An area wider than 1,400 pixels is predicted in 512 pixel squares that overlap by 64 pixels and are blended with a cosine window, so no seam shows.

The seven channels

Each channel is divided by a fixed number, so every city uses the same scale. The numbers are not fitted. This is what lets a model trained in one city read another.

Since 2026-10-23 four more channels exist, and training chooses the set: the engine's own sky view factor and the share of daylight hours the sun reaches each pixel, both read from the baseline run, and two constants for the noon sun on the design day, its elevation over 90 and which side it stands on. The model documented on this page was trained on the seven below. The comparison is issue 100.

03The network

The network is a U-Net. The name comes from the shape of the data flow: down one side of a U, across the bottom, and up the other side. Going down, each stage sees a wider area of the city at a coarser scale. Going up, each stage brings the detail back.

A parameter is one learned number: a weight in a filter, or a scale in a normalization. This network has 7,764,193. Seven kinds of stage make it up.

3 by 3 convolution
For every pixel, a weighted sum of the 3 by 3 pixels around it, across every input channel. The weights are learned. There is one set of weights for each output channel. The same weights are used at every pixel, so the stage reads geometry the same way everywhere on the tile.
Batch normalization
Rescales each channel to a steady mean and spread, so training stays stable. It has two learned numbers per channel.
ReLU
Sets negative values to zero. Without it, a stack of convolutions would collapse into one linear filter and could not learn a curve.
Max pool, 2 by 2
Keeps the largest value in each 2 by 2 block. The map becomes half as wide and half as tall. One pixel now stands for 2 m, then 4 m, 8 m and 16 m at the bottom. This is how the network sees far.
Transposed convolution, 2 by 2, stride 2
The reverse of pooling: doubles the width and height of the map, with learned weights.
Join
Stacks the upsampled map on the encoder map of the same size, so the detail lost in pooling comes back. This is the skip connection that gives the U-Net its name.
1 by 1 convolution, the head
One weighted sum over the 32 channels at each pixel. The result is the cooling at that pixel.

An encoder, a decoder or the bottleneck is one block: two 3 by 3 convolutions, each followed by batch normalization and ReLU. There are four encoders going down, four decoders coming up, and the bottleneck at the bottom.

The bars are scaled to the bottleneck, which holds 3,540,992 parameters, 46 percent of the total, and works on a map of 16 by 16 pixels. Encoder 4, the bottleneck, up 1 and decoder 1 together hold 87 percent and never see a map finer than 8 m per pixel. The stages that touch every pixel of the output, encoder 1, decoder 4 and the head, hold half a percent. Most of what the network learns is coarse.

The receptive field

The receptive field is the area of the input that one output pixel can see. A change outside that area cannot change the pixel. The field grows with each 3 by 3 convolution and doubles with each pool.

Measured on 2026-10-23 by back-propagating one output pixel to the input with every path open, the field is 188 to 204 pixels across, which is 188 to 204 m. It varies because the four pools divide the map into 16 pixel cells, and a pixel at the edge of a cell sees a little further than one at the center. The code now probes the field the same way, on a one-dimensional analog of the network, and the manifest records both ends and the method. Manifests written before 2026-10-23 recorded 152 m, an estimate from the depth alone; the two that exist were corrected by hand and say so.

A tree changes the temperature up to 71 m away (section 05). For an output pixel to see every tree that affects it, the field must be at least 142 m across. Every figure here is above that.

04Output

The output is one map. Each pixel holds the daylight-mean change in mean radiant temperature, in degrees Celsius. Daylight is 08:00 to 18:00 local time on the design day. A positive value is cooling.

The target comes from two engine runs: the untouched bundle and the bundle with the plan. The difference is the response the model learns. It is not clipped at zero. About 0.04 percent of outdoor pixels warm when a tree is added, by up to 10 C, all within 10 m of the new tree, because warm canopy replaces cold sky. The model can say so.

05How the data is made

Physics time is the budget. One engine run takes 255 to 358 s and gives one response field: the cooling at every pixel for one plan. Seventeen runs is about one and a half hours. The design set has to make each run count.

What one tree does, measured

The engine was run with single trees and the cooling was read by distance. At the planted pixel the cooling is about 18 C. It falls to under 0.1 C within 26 m in dense Ahmedabad and within 71 m in open, treeless Lagos. Beyond that distance a tree changes nothing a thermometer could read. That distance is the reach.

Superposition, and the sparse probe

When two trees are further apart than the reach, their cooling fields do not touch. The field of the pair is the sum of two single-tree fields. That is superposition. It means the two trees are two separate measurements, taken in one run.

The sparse probe design uses this. It puts about 100 single trees on a 100 m lattice, 10 by 10 across the kilometer, with a random shift of up to 35 m so the lattice does not line up with the street grid. Two trees 100 m apart overlap only in their tails. At the midpoint, 50 m from each, one tree adds about 0.1 C against a peak of 12 to 18 C, which is under 1 percent. One run therefore returns about 100 clean single-tree responses, each in its own geometric context, instead of one. Four such runs give about 400.

Why dense designs are still needed

Superposition fails when trees are close. Two trees 5 m apart do not cool twice as much as one. They shade some of the same ground, and the canopy of one replaces the cold sky that a pixel near the other would have seen. Where the sum of single-tree fields goes wrong is exactly what a simple kernel cannot predict, and exactly what a real plan with contiguous planting produces. The clustered, random and corridor designs carry that interaction signal, at coverages from 1 to 30 percent of the plantable ground.

From fields to patches

Each response field is cropped into 32 patches of 256 by 256 pixels. The crop centers are drawn at random with weights. A pixel within 80 m of a tree has weight 1.05 and any other pixel has weight 0.05. Most patches therefore hold trees, and some hold only far field, where predicting a true zero is part of the job. Ahmedabad gave 416 training patches and 128 held-out patches. Ahmedabad and Lagos together gave 832 and 256.

The split, in plain words

Training needs two sets of data. The model learns from one, the training set. It never sees the other, the held-out set, until the end. The held-out set is the test. If the model is right there, it has learned the physics and not memorized the examples. The question is how to cut the data in two.

The wrong way: by patch. The 32 patches of one design overlap. Together they cover the field about twice over, so most pixels appear in two or more patches. If some patches of a design went into training and others into the test, the model would see the same trees on the same ground in both. The test score would be too good and would mean nothing.

The way used: by design. A quarter of the designs are set aside whole, with all 32 of their patches. For Ahmedabad that is 4 of the 17 designs: clustered 5 and 10 percent, and random 5 and 10 percent. The model never sees any pixel of those plans. The test asks: given a plan it has never seen, on ground it knows, does it predict the cooling?

A second cut: by city. When several cities are trained together, a whole city can be held out instead. The model then never sees that city's ground at all. The test asks: does it transfer to geometry it has never seen? The two tests answer different questions. Section 07 reports both.

07How it is judged

Pixel error alone is the wrong measure. The response is near zero almost everywhere. A model that predicts zero everywhere has a small error and is useless. Four questions decide, in this order.

  1. Does it beat predicting nothing? Skill is 1 minus the model error over the error of predicting no change. Zero means no better than nothing. One means perfect.
  2. Does the tail survive? Error is reported by distance from a tree, from the tree itself out to 80 m. The far bands are the spillover.
  3. Is the plan score right? Plans are scored on population-weighted exposure, which integrates the whole field. That integral must be unbiased.
  4. Does it order plans correctly? A search only needs to know which of two plans is better.

08How it is used

Today the surrogate is used for one thing: assessment on designs it never trained on. No published number comes from it. Every number in the results comes from the engine.

The planners do not use it yet. Greedy and the orchard planner rank baseline harm and place trees. A surrogate-backed search is planned (issues 34 and 49). The loop below is the plan, not the present.

Every trained model lives in its own directory with a file named manifest.json. The manifest says what the model is. A reader with the manifest and no code can decide whether to trust it.

11Where models live

Models, data and results are not in git. They live under data/, which git ignores. The layout puts each tile's models beside the physics that trained them.

data/tiles/<urban center id>/<tile id>/
  bundle/        the five layers, provenance.json
  surrogate/     baseline/ and one directory per design
  models/        one directory per trained model: model.pt, manifest.json, assessment.json
data/models/     models trained on several tiles

Storing models elsewhere is an option, never a requirement. A model store interface will have three backends: a local directory, which is the default, the Hugging Face Hub, and a git-lfs repository. Each holds the same files. Fetching from a public store needs no account. Publishing needs the credential that store asks for, at build time. This is issue 103.
